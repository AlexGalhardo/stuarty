## O que você vai aprender

- o que uma cópia de segurança completa contém e como fazê-la com segurança;
- o que uma atualização faz com o espaço de trabalho;
- como reverter.

## A ideia

Tudo está em um único diretório, o [espaço de trabalho](/docs/workspace) (`/data` no contêiner, `~/.vukem-video` nos demais casos). Uma cópia de segurança completa é esse diretório. As partes que importam:

| Caminho | Guardar? |
| --- | --- |
| `db.sqlite` | sim: projetos, histórico, tarefas, usuários, chaves |
| `store/` | sim: os seus originais importados, por hash de conteúdo |
| `exports/` | sim: os arquivos que você fez |
| `artifacts/`, `frames/` | não: são refeitos a partir dos originais |
| `backups/` | as cópias do banco de dados que o servidor faz antes de uma migração |
| `logs/` | opcional |

Em um encerramento ordenado, o servidor faz o checkpoint do banco de dados, então o `db.sqlite` é autocontido quando copiado à mão. Nunca copie o espaço de trabalho enquanto o servidor roda: pare o contêiner ou o servidor antes, copie, depois inicie-o de novo.

## Início rápido

```bash
docker stop vukem-video
docker run --rm -v vukem-video:/data -v "$PWD":/backup debian:13.7-slim \
  tar -czf /backup/vukem-video-data.tar.gz -C /data .
docker start vukem-video
```

Para atualizar, baixe a nova tag e recrie o contêiner com o mesmo volume e o mesmo `APP_KEY`:

```bash
docker pull ghcr.io/alexgalhardo/vukem-video:X.Y.Z
docker stop vukem-video && docker rm vukem-video
# run the same docker run command as before, with the new tag
```

Ao iniciar, o servidor confere o banco de dados. Se há migrações pendentes e o espaço de trabalho não é novo, ele primeiro grava `backups/db-<UTC timestamp>-before-<migration>.sqlite` e mantém as cinco mais novas, depois migra. Um documento de projeto gravado por uma versão mais antiga é migrado quando é aberto, e o original é mantido no banco de dados. Leia o [changelog](/changelog) antes de uma atualização de versão menor: antes da `1.0.0`, uma versão menor pode mudar uma interface pública.

Para reverter, pare o servidor, restaure a cópia de segurança (ou o arquivo `backups/db-*-before-*.sqlite` como `db.sqlite`) e inicie a tag mais antiga. Um espaço de trabalho migrado por uma versão mais nova pode não abrir em uma mais antiga, e é por isso que você faz a cópia de segurança antes. A versão mais antiga então se recusa a iniciar, não altera nenhum arquivo e diz `this workspace was written by a newer version`, seguido do que encontrou; a saída é instalar uma versão pelo menos tão nova, ou restaurar a cópia de segurança.

### O que é testado

Cada candidata a versão é aberta contra espaços de trabalho gravados pelas versões publicadas a partir da `v0.3.0`. O workflow `upgrade` roda em todo pull request com o rótulo `release` e em toda tag, no Linux, no Windows e no macOS. Ele baixa o arquivo de cada versão, confere com o `checksums.txt`, deixa essa versão criar um espaço de trabalho com um projeto fixo (legendas, quadros-chave, um modelo, lixeira e restauração, uma exportação) e então verifica que a nova build abre cada um, grava uma cópia de segurança antes de migrar, mantém as cinco cópias mais novas, não perde nenhum projeto e não altera nenhum documento. Ele também verifica que cada binário mais antigo se recusa a abrir um espaço de trabalho gravado pela nova build. Para rodar você mesmo, a partir de um checkout, com `go`, `ffmpeg`, `ffprobe`, `jq` e `gh` instalados:

```bash
bash scripts/upgrade-test.sh v0.5.0 v0.14.0
```

Sem argumentos, o script testa todas as versões publicadas a partir da `v0.3.0`.

## Erros comuns

- Fazer a cópia de segurança apenas do banco de dados. Sem o `store/`, a sua mídia importada se perde.
- Usar a tag `latest` em um servidor que você mantém. Fixe `X.Y.Z` e mova-a de propósito.
- Executar o contêiner novo e o antigo no mesmo volume ao mesmo tempo: o segundo falha com `E_WORKSPACE_LOCKED`.
- Perder o `APP_KEY`: guarde-o com os seus outros segredos.
