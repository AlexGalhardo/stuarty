## O que você vai aprender

- qual imagem baixar e quais tags ela tem;
- o comando que a inicia e o que faz cada parte;
- como conferir que ela está rodando.

## A ideia

Toda versão estável publica uma imagem multiarquitetura (`linux/amd64` e `linux/arm64`) com o binário do Vukem Video e um FFmpeg LGPL fixado dentro. Baixe-a de qualquer um dos registros, o digest é o mesmo:

- `ghcr.io/alexgalhardo/vukem-video`
- `alexgalhardo/vukem-video` no Docker Hub

As tags são `X.Y.Z`, `X.Y` e `latest`. Fixe `X.Y.Z` para um servidor que você mantém.

Um contêiner se vincula a todas as interfaces de rede, então a imagem sempre roda em [modo de rede](/docs/self-hosting/network-mode): o login é obrigatório e o servidor precisa de um `APP_KEY`. A imagem define `HOST=0.0.0.0`, `PORT=7878`, `VUKEM_VIDEO_MODE=network`, `APP_URL=http://localhost:7878` e `VUKEM_VIDEO_HOME=/data`. Ela roda como o usuário `app` (uid 10001), grava apenas no volume `/data` e não envia dados para lugar nenhum. Nenhum servidor web roda nela: o binário Go serve o HTTP.

## Início rápido

```bash
docker run -d --name vukem-video \
  -p 127.0.0.1:7878:7878 \
  -v vukem-video:/data \
  -e APP_KEY="$(openssl rand -base64 32)" \
  -e VUKEM_VIDEO_ADMIN_EMAIL=admin@example.com \
  -e VUKEM_VIDEO_ADMIN_PASSWORD="choose-a-long-password" \
  ghcr.io/alexgalhardo/vukem-video:X.Y.Z
curl -fsS http://localhost:7878/up
```

- `-p 127.0.0.1:7878:7878` publica a porta apenas na sua própria máquina. Com o `APP_URL=http://localhost:7878` padrão, este é o único caso em que o HTTP simples é aceito.
- `-v vukem-video:/data` mantém o espaço de trabalho (banco de dados, mídia, exportações) entre as execuções do contêiner.
- O `APP_KEY` é obrigatório: 32 bytes ou mais, em base64. Ele não vem embutido na imagem, porque uma chave em uma imagem pública é pública. Guarde o valor em um lugar seguro e dê ao contêiner o mesmo valor em toda inicialização.
- As duas variáveis `VUKEM_VIDEO_ADMIN_*` criam o primeiro administrador, uma única vez, quando não existe nenhum usuário. Um contêiner nunca deixa você executar `user:create` antes da primeira inicialização, porque o servidor é dono do espaço de trabalho. Depois disso, as variáveis são ignoradas. A senha pode ser `@file:/run/secrets/admin_password` para mantê-la fora do ambiente, e o log mostra o e-mail e nunca a senha.
- O `GET /up` responde 200 quando o servidor está saudável; a imagem tem uma verificação de saúde nele. O `docker run --rm ghcr.io/alexgalhardo/vukem-video:X.Y.Z version` imprime a versão.

Para qualquer uso além de `localhost` (outra máquina, um nome de domínio), defina `APP_URL` como o endereço `https` público e coloque o TLS na frente: veja [Coloque o Caddy na frente](/docs/self-hosting/caddy).

## Erros comuns

- Publicar a porta como `-p 7878:7878`, que escuta em todas as interfaces. Use `127.0.0.1:` a menos que um proxy com TLS esteja na frente.
- Iniciar sem `APP_KEY`: o servidor sai com `APP_KEY missing`. A mensagem nomeia a variável.
- Alcançar a porta publicada de outra máquina pelo endereço do host: recusado, pois o host e a origem precisam ser `localhost:7878`.
- Iniciar um segundo contêiner no mesmo volume. Um processo é dono de um espaço de trabalho; o segundo falha com `E_WORKSPACE_LOCKED`.
