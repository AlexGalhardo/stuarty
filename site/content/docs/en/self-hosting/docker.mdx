## You will learn

- which image to pull and which tags it has;
- the command that starts it and what each part does;
- how to check that it runs.

## The idea

Every stable release publishes one multi-architecture image (`linux/amd64` and `linux/arm64`) with the Stuarty binary and a pinned LGPL FFmpeg inside. Pull it from either registry, the digest is the same:

- `ghcr.io/alexgalhardo/stuarty`
- `alexgalhardo/stuarty` on Docker Hub

The tags are `X.Y.Z`, `X.Y` and `latest`. Pin `X.Y.Z` for a server you keep.

A container binds every network interface, so the image always runs in [network mode](/docs/self-hosting/network-mode): login is mandatory and the server needs an `APP_KEY`. The image sets `HOST=0.0.0.0`, `PORT=7878`, `STUARTY_MODE=network`, `APP_URL=http://localhost:7878` and `STUARTY_HOME=/data`. It runs as the user `app` (uid 10001), writes only to the `/data` volume and sends no data anywhere. No web server runs in it: the Go binary serves HTTP.

## Quick start

```bash
docker run -d --name stuarty \
  -p 127.0.0.1:7878:7878 \
  -v stuarty:/data \
  -e APP_KEY="$(openssl rand -base64 32)" \
  -e STUARTY_ADMIN_EMAIL=admin@example.com \
  -e STUARTY_ADMIN_PASSWORD="choose-a-long-password" \
  ghcr.io/alexgalhardo/stuarty:X.Y.Z
curl -fsS http://localhost:7878/up
```

- `-p 127.0.0.1:7878:7878` publishes the port on your own machine only. With the default `APP_URL=http://localhost:7878` this is the one case where plain HTTP is accepted.
- `-v stuarty:/data` keeps the workspace (database, media, exports) across container runs.
- `APP_KEY` is required: 32 bytes or more, base64. It is not baked into the image, because a key in a public image is public. Store the value somewhere safe and give the container the same one on every start.
- The two `STUARTY_ADMIN_*` variables create the first administrator, once, when no user exists. A container never lets you run `user:create` before the first start, because the server owns the workspace. Afterwards the variables are ignored. The password may be `@file:/run/secrets/admin_password` to keep it out of the environment, and the log shows the email and never the password.
- `GET /up` answers 200 when the server is healthy; the image has a health check on it. `docker run --rm ghcr.io/alexgalhardo/stuarty:X.Y.Z version` prints the version.

### Your first export from the container

The container has no files of yours and the CLI needs a key, so three more steps lead to a verified export. Run them in a shell on the host.

1. Give the container a folder to import from. In network mode an import is confined to `STUARTY_IMPORT_ROOTS`, so mount a folder with your clip and name it (add the two lines to the `docker run` above; on Windows with Git Bash set `MSYS_NO_PATHCONV=1` so `/media` is not rewritten):

   ```bash
   -v "$HOME/clips:/media:ro"    -e STUARTY_IMPORT_ROOTS=/media    ```

2. Create an API key with the administrator you made (the secret is shown once; see [API keys](/docs/self-hosting/api-keys)):

   ```bash
   APP=http://localhost:7878
   curl -fsS -c jar.txt -H "Content-Type: application/json" -H "Origin: $APP"      -d '{"email": "admin@example.com", "password": "choose-a-long-password"}' "$APP/auth/login"
   curl -fsS -b jar.txt -H "Content-Type: application/json" -H "Origin: $APP"      -d '{"name": "first-export", "scopes": ["read", "edit", "media", "render"]}' "$APP/api/v1/keys"
   ```

3. Run the CLI inside the container with the key. The server owns the workspace, so the CLI talks to it as a client; inside the container the address is already `http://localhost:7878`. The server chooses the project id (`project:create --id` is refused in network mode): use the ids the commands print.

   ```bash
   export STUARTY_KEY="vvk_<the secret from step 2>"
   vv() { docker exec -i -e STUARTY_KEY stuarty stuarty "$@"; }
   vv project:create --name "First export" --json \
     --description "The first export of this server: one clip, cut and exported as a video, to check the install." \
     --specific "Export the first video of this server" --measurable "The file plays from start to end" \
     --achievable "One clip in the import folder is enough" --relevant "It proves the server can export" \
     --time-bound "Done within the next ten minutes" --due 2027-03-31   # prints project_id
   vv item:add --project <project id> --kind timeline --title "First export"
   vv media:import /media/clip.mp4 --project <project id> --json   # prints asset_id
   vv edit --project <project id> --ops - <<'EOF'
   [{"op":"track.add","args":{"kind":"visual","name":"Video","id":"trk_f6g7h8j9k0"}},
    {"op":"clip.add","args":{"track_id":"trk_f6g7h8j9k0","asset_id":"<asset id>","start":"0s","duration":"2s","id":"itm_m1n2p3q4r5"}}]
   EOF
   vv export --project <project id>
   ```

   The last command waits and prints `succeeded`; the file is in `/data/exports/<project id>/<job id>.mp4` and `vv job:show <job id>` lists the checks it passed. A clip with sound and a 1080x1920 picture exports as is; see [Exporting](/docs/guide/exporting) for formats and `--out`. `scripts/first-export-timing.sh` in the repository runs these steps and times them.

### Plain HTTP is safe only on the loopback address

The container serves plain HTTP for `APP_URL=http://localhost:7878`, and nothing on that listener is encrypted. That is safe only when the port is published on your own machine, with `-p 127.0.0.1:7878:7878` (or `[::1]`), or when TLS is in front. Inside a container the server cannot see how the port is published, so when it listens on a non-loopback address over plain HTTP it logs this warning (the address is the one it binds):

```text
network mode over plain HTTP on 0.0.0.0:7878: no credential is encrypted on this listener, so publish the port on the loopback address only (docker run -p 127.0.0.1:<port>:<port>); on any other interface a password and a session cookie cross the network in clear
```

If you see it, republish the port on `127.0.0.1`, or terminate TLS in the server or in a proxy.

For any use other than `localhost` (another machine, a domain name), set `APP_URL` to the public `https` address and put TLS in front: see [Put Caddy in front](/docs/self-hosting/caddy).

## The key of the credential vault

When you connect an account (the Connections page), Stuarty keeps its credential in an encrypted file, `vault.json`, in the workspace. The key that opens it is never in the workspace, so a copy of the volume reveals no credential. Give the container the key once, as a Docker secret:

```bash
openssl rand -base64 32 > master.key
docker run -d --name stuarty \
  -p 127.0.0.1:7878:7878 \
  -v stuarty:/data \
  -v "$PWD/master.key:/run/secrets/master_key:ro" \
  -e STUARTY_MASTER_KEY_FILE=/run/secrets/master_key \
  ghcr.io/alexgalhardo/stuarty:X.Y.Z
```

Add the other variables of the command above (`APP_KEY` and the first administrator) to the same `docker run`.

`STUARTY_MASTER_KEY` takes the key itself instead of a file. Keep a copy of the key next to your backups: without it the connections cannot be opened and you connect the accounts again (projects and media are not encrypted and are not affected). Nothing is created until the first credential, so a server with no connection needs no key.

## Common mistakes

- Publishing the port as `-p 7878:7878`, which listens on every interface: a password and a session cookie then cross the network in clear, and the server logs the warning above. Use `127.0.0.1:` unless a proxy with TLS is in front.
- Starting without `APP_KEY`: the server exits with `APP_KEY missing`. The message names the variable.
- Reaching the published port from another machine by the address of the host: refused, since the host and origin must be `localhost:7878`.
- Importing a file the server cannot reach: the CLI runs inside the container, so the path is a path in the container, and it must be inside `STUARTY_IMPORT_ROOTS`. A path outside it answers `E_FILE_NOT_FOUND`, the same as a missing file.
- Starting a second container on the same volume. One process owns a workspace; the second fails with `E_WORKSPACE_LOCKED`.
