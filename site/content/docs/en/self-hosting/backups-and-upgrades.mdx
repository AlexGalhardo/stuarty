## You will learn

- what a complete backup contains and how to take one safely;
- what an upgrade does to the workspace;
- how to roll back.

## The idea

Everything is in one directory, the [workspace](/docs/workspace) (`/data` in the container, `~/.stuarty` otherwise). A complete backup is that directory. The parts that matter:

| Path | Keep? |
| --- | --- |
| `db.sqlite` | yes: projects, history, jobs, users, keys |
| `store/` | yes: your imported originals, by content hash |
| `exports/` | yes: the files you made |
| `artifacts/`, `frames/` | no: they are rebuilt from the originals |
| `backups/` | the database copies the server makes before a migration |
| `logs/` | optional |

On a graceful shutdown the server checkpoints the database, so `db.sqlite` is self-contained when copied by hand. Never copy the workspace while the server runs: stop the container or the server first, copy, then start it again.

## Quick start

```bash
docker stop stuarty
docker run --rm -v stuarty:/data -v "$PWD":/backup debian:13.7-slim \
  tar -czf /backup/stuarty-data.tar.gz -C /data .
docker start stuarty
```

To upgrade, pull the new tag and recreate the container with the same volume and the same `APP_KEY`:

```bash
docker pull ghcr.io/alexgalhardo/stuarty:X.Y.Z
docker stop stuarty && docker rm stuarty
# run the same docker run command as before, with the new tag
```

On start the server checks the database. If migrations are pending and the workspace is not new, it first writes `backups/db-<UTC timestamp>-before-<migration>.sqlite` and keeps the five newest, then migrates. A project document written by an older version is migrated when it is opened, and the original is kept in the database. Read the [changelog](/changelog) before a minor upgrade: before `1.0.0` a minor release may change a public interface.

To roll back, stop the server, restore the backup (or the `backups/db-*-before-*.sqlite` file as `db.sqlite`) and start the older tag. A workspace migrated by a newer version may not open in an older one, which is why you take the backup first. The older version then refuses to start, changes no file and says `this workspace was written by a newer version`, followed by what it found; the fix is to install a version at least as new, or to restore the backup.

### Coming from Vukem Video

Stuarty is the product that was called Vukem Video up to `v0.29.0`; the version numbers continue. Nothing has to be done to keep your projects.

- **The workspace folder.** At its first start Stuarty looks for `~/.stuarty`. When that folder does not exist and `~/.vukem-video` does, it copies the database to `backups/adopt-<UTC timestamp>/`, renames the folder to `~/.stuarty` (or, when the two are on different volumes, copies it, checks every file and leaves a `MOVED-TO-STUARTY.txt` note in the old folder), writes `adopted.json` in the new one and prints one line that says so. The old folder is never deleted. A server or desktop application of Vukem Video that is still running stops the adoption: close it first. When both folders exist, `~/.stuarty` is used and one line names the old one.
- **The variables.** `VUKEM_VIDEO_HOME` and every other `VUKEM_VIDEO_*` variable is still read, until `1.0.0`, when the matching `STUARTY_*` variable is not set. Each use prints one warning; set the new name to silence it. The table of pairs is in the [configuration reference](/docs/reference/configuration).
- **The command.** `vukem-video` is now `stuarty`. A package of Vukem Video is replaced by the `stuarty` package.
- **The container.** The image is `ghcr.io/alexgalhardo/stuarty` (and `alexgalhardo/stuarty` on Docker Hub). A Docker volume keeps the name you gave it: keep `-v vukem-video:/data` to keep your data, or copy the volume once if you prefer the new name.

### What is tested

Every release candidate is opened against workspaces written by the published releases from `v0.3.0` on. The `upgrade` workflow runs on every pull request labelled `release` and on every tag, on Linux, Windows and macOS. It downloads the archive of each release, checks it against `checksums.txt`, lets that release create a workspace with a fixed project (captions, keyframes, a template, trash and restore, an export), and then checks that the new build opens each one, writes a backup before migrating, keeps the five newest backups, loses no project and changes no document. It also checks that each older binary refuses a workspace written by the new build. To run it yourself, from a checkout, with `go`, `ffmpeg`, `ffprobe`, `jq` and `gh` installed:

```bash
bash scripts/upgrade-test.sh v0.5.0 v0.14.0
```

Without arguments the script tests every published release from `v0.3.0` on.

## Common mistakes

- Backing up only the database. Without `store/` your imported media is gone.
- Using the tag `latest` on a server you keep. Pin `X.Y.Z` and move it on purpose.
- Running the new and the old container on one volume at the same time: the second fails with `E_WORKSPACE_LOCKED`.
- Losing `APP_KEY`: keep it with your other secrets.
