# 46: The own FFmpeg build, signed and adopted

## Goal

A creator installs Stuarty and exporting just works, with hardware encoding where their machine has it, without hunting for an FFmpeg: because the project ships its own LGPL build, reproducible and signed.

## Context and related decisions

- ADR-0011 (FFmpeg distribution and codec policy: only LGPL, as a separate process, the GPL filters absent), ADR-0025 and ADR-0028 (releases, suspended), ADR-0045 (releases deferred).
- PRD-003 RF-209, NFR-043; SDD-011 section 8; SDD-009.
- `scripts/ffmpeg-build.sh`, `scripts/ffmpeg-pin.sh`, `scripts/ffmpeg-verify.sh`, `scripts/ffmpeg-filters.txt`, `internal/tools/ffmpegconf`, `ffmpegfresh`, `ffmpegpins`, the OpenH264 manifest in `engine/ffmpeg`.
- Absorbs the earlier plans on the own FFmpeg build pipeline and its adoption.

## Scope

- Modules: the build scripts and tools above, `engine/ffmpeg/` (discovery of the bundled build, the encoder allow-list), `.config/` (build definitions), the installers and the Docker image (which FFmpeg they carry), SDD-011, SDD-009, `licenses/`.

## Out of scope

- Any GPL or non-free component, in any configuration.
- Building for systems that have no real machine to verify on (they follow epic 43).

## Dependencies

**Blocked until there is a release to carry the build's assets** (releases are deferred by ADR-0045). The other question is settled: H.264 software encoding stays an optional download of Cisco's OpenH264 binary at an explicit install step, which is the mechanism in the code today (author decision D-087). One manual step belongs to the author when the epic starts: running the OpenH264 install once on the machine, because an agent is not allowed to download that binary; the goldens that depend on it are recalculated after that. Technically after 35.

## Technical design

- **Reproducible**: the build is defined by pinned source archives with digests measured from real downloads (`ffmpeg-pin.sh`, a working convention of `AGENTS.md` section 9), a fixed configure line generated by `ffmpegconf`, and a container image with a fixed tag; two builds on the same host produce the same digest.
- **What it contains**: exactly the decoders, demuxers, muxers, filters (`scripts/ffmpeg-filters.txt`, extended only for filters the engine references) and encoders the product uses; the hardware encoder interfaces of each system; the permissively licensed AV1 encoder chosen in epic 35 if the author approves it. `ffmpeg-verify.sh` asserts the licence line, the absence of GPL filters and encoders, and the presence of each required component.
- **H.264**: OpenH264 by explicit install (author decision D-087). The pinned manifest and its verification remain as they are; the build never bundles the library and never downloads it on its own; hardware encoders are used where the machine has them.
- **Adoption**: the installers and the Docker image carry the own build; discovery prefers it; a user's own FFmpeg remains possible through the existing setting, with the existing licence classification.
- **Provenance**: digests, the configure line, the source list and the licence texts are published with the build and included in `licenses/` and the notices.
- **Freshness**: `ffmpegfresh` reports when a pinned source has a newer security release.

## Test strategy

- Reproducibility: two builds, one digest.
- Verification script: licence, required and forbidden components.
- The engine suites and the reference export against the own build.

## Acceptance criteria

1. Two builds of the same pins give identical digests.
2. `ffmpeg-verify.sh` confirms an LGPL build with no GPL filter or encoder and with every component the engine references.
3. A fresh install exports the reference project with no FFmpeg supplied by the user.
4. Hardware encoders are found on machines that have them.
5. The build's sources, configure line, digests and licences are published with it.

## Risks and mitigation

- **A licence mistake in the configuration.** Mitigation: the verify script is the gate; a GPL component fails the build.
- **Patents on codecs.** The H.264 path is the author's decision (D-087) and this epic implements it without widening it. **STOP** if the build would have to bundle or fetch the library by itself, and for the release that carries the assets.
