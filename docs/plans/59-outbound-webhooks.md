# 59: Outbound webhooks

## Goal

A creator connects Stuarty to the tools they already use (Zapier, n8n, Make, Discord, their own server) by registering a URL that is told when something happens: a post went out, an export is ready, an approval is waiting, a job failed.

## Context and related decisions

- Author decision D-121 (2026-11-20): outbound only; no inbound webhooks.
- ADR-0032: outbound only to connected destinations, no telemetry. A webhook URL is a destination the user registers, so it is a connection in the sense of ADR-0032; with no webhook registered, nothing goes out.
- ADR-0033: secrets only in the vault; no tool returns one. The signing secret of a webhook is a vault secret.
- The events the product already publishes on its event bus (SDD-000 events, the jobs, approvals and publications of SDD-015, SDD-016 and SDD-020).

## Scope

- Modules: `core/` (the webhook, its events, the payload and signature rules), `service/` (CRUD, delivery, retries, history, test send), the store and a migration, the adapters (HTTP, MCP, CLI), `web/resources/js/pages/Webhooks/`, the sidebar entry, SDD-000 and a new SDD section (or SDD), the threat model, the user docs.
- Must not touch: the sidebar footer, sign-in, the vault key handling (epic 57), the projects page (epic 56).

## Out of scope

- Inbound webhooks; custom payload templates; per-project filters beyond the event list.

## Dependencies

04 (vault), 05 (approvals), 30 (jobs). Next to epic 57: deliveries need the server unlocked once 57 lands; while locked, deliveries wait and are sent after unlock.

## Technical design

- **A webhook:** a name, an `https://` URL (`http://` only for a loopback host), the events it receives, enabled or not, and a signing secret generated by the server and kept in the vault (shown once at creation, rotatable).
- **Payload:** JSON with `event`, `id`, `occurred_at`, `workspace`, and only ids and metadata of the subject (project id, job id and kind and state, publication id, network, URL of the published post when public). Never a credential, a token, a file, a text body or a prompt.
- **Delivery:** POST with `Content-Type: application/json`, `Stuarty-Signature: t=<unix>,v1=<hex HMAC-SHA256 of "t.body">`, a timeout of 10 s, up to 5 retries with exponential backoff on network errors and 5xx, no redirects followed; each attempt is recorded (status, duration, error, truncated response size, never the response body). A "send test" action delivers a `webhook.test` event.
- **Security:** the URL host is checked against private and link-local ranges unless it is loopback chosen explicitly (SSRF); the resolved address is checked again at connect time (DNS rebinding); threat-model entries with the next free ids.
- **Surfaces:** create, list, update, delete, rotate secret, send test, list deliveries, redeliver, on HTTP, MCP and CLI with parity; creating a webhook is a person action (an agent can prepare it for approval).
- **UI:** a Webhooks page (list, create with the event checklist and a clear explanation of each event, the secret shown once with copy, deliveries with status and redeliver), and a sidebar entry.

## Acceptance criteria

1. With no webhook registered, the product opens no outbound connection (the no-egress test still passes).
2. A registered webhook receives the chosen events, signed, and the signature verifies with its secret.
3. No payload carries a credential, a token or a content body (a test over every event).
4. A private-range or rebinding URL is refused.
5. Deliveries are listed with their status and can be resent; the test send works.
6. `task lint`, `task test`, `task test:web`, `go test -run TestSecurity_ ./...` pass; no new dependency.

## Risks and mitigation

- SSRF and data leaks: the URL rules, the check at connect time, the metadata-only payload, all tested.
- A slow receiver blocks other work: deliveries run on their own bounded worker, never in the request.
