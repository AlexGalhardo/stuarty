# ADR-0017: HTTP API with OpenAPI; real-time by server-sent events

- Status: Accepted (2026-11-14)
- Deciders: architect
- Links: stack trade-offs §2, §6, engine §4, ADR-0006, ADR-0008, SDD-003, SDD-006

## Context

The UI, external API clients and the CLI in server mode all talk to the owner process. The stack draft listed REST with OpenAPI and "WebSocket/SSE". vukem has typed handlers that generate OpenAPI and clients, and server-sent events in its core with a topic hub and `Last-Event-ID`; WebSocket is a separate module at version 0.1. Figma's design shows that an authoritative server ordering events is enough for a document of objects with properties.

## Decision

1. One HTTP API under `/api/v1`, JSON in and out, one endpoint per `Service` method. Timeline changes use a single endpoint, `POST /api/v1/projects/{id}/edit`, that takes the same batch as the MCP `edit` tool.
2. The OpenAPI 3.1 document is generated by vukem from the typed handlers and published by the server and on the documentation site.
3. Real-time is **server-sent events**: `GET /api/v1/projects/{id}/events`. Commands go up as HTTP requests; events come down the stream. No WebSocket.
4. An event is a committed batch: project, revision, actor, the operations' diff and a timestamp. Job progress and ingest progress are events on the same stream.
5. Events for a project carry consecutive revisions. A client that sees a gap, or reconnects, sends the last revision it has (`Last-Event-ID`); the server replays from the log, or tells the client to reload the document if the gap is too large.
6. The response to an edit and the event stream both carry the revision, so a client applies whichever arrives first and ignores the other.
7. Errors use one envelope with a stable code, message, hint and `retryable` flag (SDD-002), with matching HTTP status.
8. Binary content (proxies, thumbnails, rendered frames, exports) is served by dedicated endpoints with HTTP Range and cache headers keyed by content hash.

## Alternatives

- **WebSocket for commands and events.** One connection, but vukem's WebSocket is a young separate module, and request and response already fit HTTP.
- **Polling.** Simple; too slow for "a human and an agent see the same result".
- **gRPC or JSON-RPC for the API.** No consumer needs them; REST with OpenAPI is what agents and scripts expect.

## Consequences

Positive: built entirely from what the vukem core provides; `EventSource` reconnects on its own.

Positive: replay from the log makes reconnection exact.

Negative: server-sent events are one-way and text only; fine for this protocol.

Negative: HTTP/1.1 limits a browser to six connections per origin, and an event stream holds one; the UI opens one stream per open project, not per component.
