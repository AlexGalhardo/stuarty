# Rust

Rust exists in this repository for one reason: the pixel renderer of ADR-0029 (D-035). These rules apply to everything under `renderer/` and to the code that hosts it.

1. Rust lives only in `renderer/` and, for the native capture helper, in `capture/` (ADR-0049, where rules 2 to 4, 7 and 8 apply and the crates it lists are approved) and, for the local AI helper, in `aihelper/` (ADR-0050, where rules 2 to 4, 7 and 8 apply; the one crate approved for it is `ort`, the ONNX Runtime binding, D-139: it loads the pinned official ONNX Runtime library from a path and the build downloads nothing). The command core, the frame plan (`core/plan`), the service, the agent surfaces and the UI stay in Go and TypeScript. A renderer never interpolates, never reads the document and never decides what a frame contains: it draws the frame plan it receives (AGENTS.md rules 1 and 5).
2. Toolchain: the stable Rust pinned in `rust-toolchain.toml` (with the `wasm32-unknown-unknown` target, `rustfmt` and `clippy`); `Cargo.lock` is committed; every crate is at an exact version (`=x.y.z`). Approved by D-035: `wgpu`, `wasm-bindgen` and its CLI, `bytemuck`, `cargo-deny`; `wazero` on the Go side. Approved on 2026-11-16 for the text port (P5-RND-006): `harfrust`, `skrifa`, `unicode-bidi`, `unicode-linebreak` and `unicode-script` (replacing `rustybuzz` and `ttf-parser`, which RustSec lists as unmaintained). Approved by D-139 for `aihelper/` only: `ort` (MIT OR Apache-2.0), with its own dependencies as cargo resolves them, at `=2.0.0-rc.15` because the project has published no other 2.x version and no 1.x version supports the pinned runtime. This is a **temporary exception to the "no rc" rule, approved by the author (D-141), for this one crate only**: swap it for the stable 2.0.0 as soon as that release exists, and never extend the exception to another dependency; the `load-dynamic` feature loads the official ONNX Runtime library (MIT, pinned by SHA-256) from a path, so no build step downloads a binary. For `capture/` only, ADR-0049 approves `windows-capture`, `wasapi`, `cpal` and, by D-142 (2026-11-24), the `windows` crate at the exact locked version (0.62.2) for Media Foundation. Any other crate, build dependency or tool needs the author's approval first, like any dependency (AGENTS.md rule 9).
3. Before every commit that touches `renderer/`: `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test`, `cargo deny check`. The licence allowlist of `renderer/deny.toml` comes from `internal/tools/notices`; never add a licence to one without the other. No GPL, LGPL-linked or unknown-licence crate.
4. No `unsafe` outside the reviewed boundary modules (the WebAssembly exports and the native process I/O). Each `unsafe` block carries a `// SAFETY:` comment, and a new one needs the orchestrator's review.
5. The CPU path is the truth and must be bit-exact on Linux, macOS, Windows and in WebAssembly: integer or fixed-point arithmetic for every value that reaches a pixel, no `f32`/`f64` in the blend or sampling of the CPU path, no platform SIMD intrinsics whose results differ, no iteration over a `HashMap` that affects output, no thread count that changes results. Floating point is allowed in the GPU path only, held by the tolerance of SDD-013.
6. The WebAssembly module imports nothing from its host except memory: no WASI, no clock, no random, no file or network. `wazero` runs it with a memory limit; the browser runs it in a worker. A new import is a security change (SDD-007 threat row first).
7. No cgo, ever. The Go export reaches the renderer through `wazero` or, for the optional native GPU host, through a child process under the FFmpeg process policy (SDD-007 §6).
8. Every input that crosses the boundary (frame plan, decoded frames, fonts) is validated with explicit limits (size, layer count, dimensions) and fails with an error code from SDD-000, never a panic. The plan decoder and the composition are fuzzed.
9. Builds are reproducible: `scripts/build-renderer.sh` with `SOURCE_DATE_EPOCH`, `--remap-path-prefix` and a fixed build path. The module's SHA-256 is checked where Go embeds it and where the browser loads it; two clean builds give the same digest. The Linux runner and a Windows machine build the same bytes: cargo hashes the host line of `rustc -vV` into the symbols of every crate, so off x86-64 Linux the script builds with `internal/tools/rustchost`, which reports the host of the runner in that line (epic 93; `internal/tools/wasmdiff` compares two modules).
10. A change of the renderer's output is proven by the parity gates of `skills/renderer-parity/`, never by eye.
