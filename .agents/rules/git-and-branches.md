# Git and branches

The process is the release train of ADR-0048: the open release pull request is the integration line, approved work joins it as linear commits, and each release is rebase-merged into `main` when it holds about 90 commits. The tool is `bash .agents/skills/release-pr/scripts/release-train.sh` (`status`, `integrate`, `cut`); the procedure is `skills/release-pr/`.

1. Never commit or push to `main` directly. `main` changes only through the rebase-merge of a release pull request by the release train. No tag is pushed with git: each cut publishes its GitHub release with the changelog as notes, with the `release` workflow paused (ADR-0048 item 5).
2. **The integration branch is the open release branch**, `release/vX.Y.Z` (or `release/vX.Y.Z-r2` when a name was spent), with its pull request against `main` (`release-train.sh status` names both). It is linear: no merge commit, ever, because GitHub refuses to rebase a pull request that needs one. Every epic is a branch from its tip, `epic/NN-<slug>`, and a fix of the feedback queue is `fix/VV-NNN-<slug>`. Epic and fix branches are never pushed and never get pull requests of their own.
3. **Only the orchestrator pushes, and only the open release branch**, after integrating work the specialist approved, so that the release pull request shows what is finished. Never push a branch whose local checks failed.
4. **Each agent works in its own worktree outside the repository folder**, in the sibling folder `stuarty-worktrees/<agent>`, created by the orchestrator from the tip of the release branch. Parallel agents and worktrees need the author's explicit yes; the work-session prompt carries it.
5. **The orchestrator integrates an approved branch with `release-train.sh integrate <branch>`**: it cherry-picks, in order and with `-x`, the commits of the branch that are not on `main`, on a release branch or already on the line by patch, and skips the branch's merge commits. A conflict stops it: resolve, `git cherry-pick --continue`, run `integrate` again. Then remove the worktree and the local branch. Shared files (`rules/plans.md` section 4) are integrated one epic at a time.
6. A long epic is updated by merging the release branch into it (the merge commits stay on the epic branch; `integrate` leaves them out), never by rebasing commits another agent may have based work on.
7. Never `git stash`, `git reset --hard`, `git checkout -- .`. `git reset --soft` to squash your own unpushed commits is fine. No force push.
8. Chain with `&&`. Never pipe a check into `tail` or `head` before a push: the pipe hides the exit code. Write the output to a file, test `$?`, then push.
9. **The cut.** At 88 commits or more (`release-train.sh cut`), and on its own at 95 while `integrate` runs, the train writes the changelog section of the release (every commit since the last `chore(release)` on `main`, linked), commits `chore(release): vX.Y.Z`, pushes, rebase-merges the pull request with `gh pr merge --rebase --admin`, waits until `main` carries the tree, and starts `release/v<next minor>` from the new `main`; the next pull request opens with its first integrated commit. GitHub refuses a rebase-merge above 100 commits, so a release never holds more than 96. An epic or fix branch that was cut from a release that has since been merged is integrated the same way: only its own commits are picked.
10. Old worktrees and merged branches are removed when their epic is done. A branch that was deleted on 2026-11-18 can be recovered from the maintainers' backup bundle; ask the author. The former integration branch `release/0.30.0` and its draft pull request #106 are frozen as the backup of the history before the train; nothing is pushed to them.
